3. Create raw SQL migration for append-only enforcement and partitioning. Add a file `packages/shared/prisma/sql/append_only_rules.sql`:

```sql
-- Append-only enforcement (per D-13, Pitfall 6 in RESEARCH.md)
-- Using RAISE EXCEPTION triggers instead of silent DO INSTEAD NOTHING rules

CREATE OR REPLACE FUNCTION prevent_update_delete()
RETURNS TRIGGER AS $$
BEGIN
  RAISE EXCEPTION 'UPDATE and DELETE operations are not allowed on append-only table %', TG_TABLE_NAME;
  RETURN NULL;
END;
$$ LANGUAGE plpgsql;

-- Apply to all three append-only tables
CREATE TRIGGER no_update_ledger_entries
  BEFORE UPDATE OR DELETE ON "LedgerEntry"
  FOR EACH ROW EXECUTE FUNCTION prevent_update_delete();

CREATE TRIGGER no_update_audit_logs
  BEFORE UPDATE OR DELETE ON "AuditLog"
  FOR EACH ROW EXECUTE FUNCTION prevent_update_delete();

CREATE TRIGGER no_update_agent_action_logs
  BEFORE UPDATE OR DELETE ON "AgentActionLog"
  FOR EACH ROW EXECUTE FUNCTION prevent_update_delete();
```

Note: Monthly partitioning (DATA-06) is deferred to a post-migration SQL script because Prisma does not natively support PostgreSQL partitioned tables. The SQL file `packages/shared/prisma/sql/partitioning.sql` should contain:

```sql
-- Monthly partitioning for audit/ledger tables (per D-13)
-- This converts the tables to partitioned tables
-- Run AFTER initial Prisma migration

-- Create partition function
CREATE OR REPLACE FUNCTION create_monthly_partition(
  table_name TEXT,
  partition_date DATE DEFAULT CURRENT_DATE
) RETURNS VOID AS $$
DECLARE
  partition_name TEXT;
  start_date DATE;
  end_date DATE;
BEGIN
  start_date := date_trunc('month', partition_date);
  end_date := start_date + INTERVAL '1 month';
  partition_name := table_name || '_' || to_char(start_date, 'YYYY_MM');

  EXECUTE format(
    'CREATE TABLE IF NOT EXISTS %I PARTITION OF %I FOR VALUES FROM (%L) TO (%L)',
    partition_name, table_name, start_date, end_date
  );
END;
$$ LANGUAGE plpgsql;

-- Note: Converting existing tables to partitioned requires recreating them.
-- For a greenfield project, create partitioned tables BEFORE first data insertion.
-- Prisma will be configured to query the parent table; PostgreSQL routes to partitions.
```

1. Create `packages/shared/src/crypto.ts` (per D-12, RESEARCH Pattern 4):

Implement `CryptoService` class:
- Constructor takes `keyConfig: { version: number; key: string }[]` where key is hex-encoded 32-byte AES key
- `encrypt(plaintext: string): EncryptedPayload` — uses `crypto.randomBytes(12)` for 96-bit IV (NEVER reuse), `createCipheriv('aes-256-gcm', key, iv)`, returns `{ ciphertext: base64, iv: base64, tag: base64, keyVersion: number }`
- `decrypt(payload: EncryptedPayload): string` — looks up key by payload.keyVersion, uses `createDecipheriv`, calls `setAuthTag`
- Export `EncryptedPayload` interface
- Factory function `createCryptoService()` that reads from `process.env.ENCRYPTION_KEY` and `process.env.ENCRYPTION_KEY_VERSION`

CRITICAL: Every encrypt call MUST generate a fresh IV via `randomBytes(12)`. Never accept IV as input. This is per NIST SP 800-38D.

2. Create `packages/shared/src/hmac.ts` (per D-13, DATA-05):

Implement:
- `computeRowHmac(fields: Record<string, unknown>): string` — sorts keys alphabetically, concatenates `key:JSON.stringify(value)` with `|` separator, creates HMAC-SHA256 with `process.env.HMAC_SECRET_KEY`, returns hex digest
- `verifyRowHmac(fields: Record<string, unknown>, expectedHmac: string): boolean` — computes HMAC and uses `crypto.timingSafeEqual` for constant-time comparison

| Boundary | Description |
|----------|-------------|
| App -> Database | Encrypted Tier 1 fields cross this boundary as ciphertext |
| Env -> App | Encryption keys and HMAC keys loaded from environment |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-02 | Information Disclosure | CryptoService | mitigate | AES-256-GCM with per-record random IV, key stored in env var not DB (per D-12) |
| T-01-03 | Tampering | Append-only tables | mitigate | PostgreSQL triggers RAISE EXCEPTION on UPDATE/DELETE; HMAC checksums on each row (per D-13) |
| T-01-04 | Tampering | HMAC key exposure | mitigate | Separate HMAC_SECRET_KEY env var, not same as ENCRYPTION_KEY |
| T-01-05 | Information Disclosure | IV reuse | mitigate | randomBytes(12) per encrypt call, IV never accepted as input |
| T-01-06 | Tampering | Audit log bypass | mitigate | Database-level triggers prevent circumventing app-level controls |
</threat_model>
